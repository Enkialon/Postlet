## 2. 必须保留的正确性基线

以下复杂度有实际业务或安全问题作为依据，不能以“简化”为由删除：

1. Message 属于一个 Account、一个 Session，最多对应一个远端位置；不同位置独立，同位置重复同步幂等。移动仍是旧位置移出、新位置新增。
2. UIDVALIDITY 变化必须隔离旧代；固定 mutation 目标、位置修订和文件夹绑定修订继续阻止旧操作误作用于新目标。
3. 同步取消后必须等待实际阻塞线程退出；账号 permit 由实际执行任务持有，不能只因等待者取消就提前释放。
4. 新凭据先写到独立引用，再与配置同事务切换；数据库失败时只清理确认未被引用的新凭据。
5. 凭据继续加密存储，保留原子替换、秘密隔离和必要的跨进程保护。
6. Graph OAuth 继续使用；通用 IMAP/SMTP V1 仅支持密码、应用密码或邮箱授权码。
7. 所有协议访问仍在 Rust infrastructure；前端经 Port/Adapter 调用。
8. 保留当前有界下载与 UID 差集正确性基线，不因本次简化引入未经验证的高水位增量算法。

不新增 Repository/TransactionManager trait、Rust interfaces 层、通用锁管理框架、通用事件总线或通用补偿工作流。

## 3. S-01：将 FLAGS 更新限制到必要字段

### 3.1 原来的逻辑

主要位置：

- `infrastructure/imap/sync.rs::sync_folder`
- `application/use_cases/sync_use_case.rs::apply_remote_flags`
- `infrastructure/repository/messages.rs::{get_by_location, upsert_with_recipients}`
- `infrastructure/repository/sessions.rs::recompute_projection`

执行流程：

```text
对已下载且远端仍存在的 UID 批量获取 FLAGS
  → 把 FLAGS 合入本轮新下载的 Upsert 快照
  → 又把全部观测转换为 FlagsChanged，包括刚合入快照的邮件
  → application 按每条 FlagsChanged 查询完整 Message 和收件人
  → 查询当前有效本地意图，合成展示标志
  → upsert_with_recipients 重写整行 Message
  → DELETE 全部收件人，再逐条 INSERT 相同收件人
  → 每条邮件分别重算 Session 投影
```

即使没有任何标志变化，该路径也更新 local_updated_at、写邮件和收件人，并把相关 ID 加入 ChangeSet。

### 3.2 原因与影响

显式 FlagsChanged 的模型已经建立，但保存入口仍按完整邮件快照设计，局部变更语义没有落实到持久化操作范围。

字段范围收敛本身不能证明观测仍有效：位置消失后重现、绑定/代次变化，以及读取发起后已有较新 mutation 确认，都可能使迟到 FLAGS 过期。当前固定 mutation 目标的校验不能自动保护一个仅按 remote_key 更新的 FLAGS 入口。

- 为几个布尔观测重写正文、地址和收件人，扩大了读写范围和维护责任。
- 新下载邮件可能先应用 Upsert，再应用相同 FLAGS，造成重复处理。
- 同一 Session 有 N 封邮件被核对时，会重复计算 N 次未读数和最新邮件。最坏情况下反复扫描同一会话的大量消息；具体耗时需测量，不能直接宣称达到某个加速倍数。
- 未变化的轮询也产生无意义写入和 UI 失效。

### 3.3 拟修复的逻辑

1. 保留 RemoteFlags 的三态观测：None 为未观测，Some(false) 为明确清除，Some(true) 为明确设置。
2. 已合入 Upsert 的本轮新快照，不再追加同一次观测的 FlagsChanged。已有邮件的独立 FLAGS 观测仍保留。
3. 在 messages 仓储增加或复用一个限定字段的模块函数，仅处理 remote_is_read、remote_is_draft、remote_is_deleted、必要的 is_read/is_draft 展示缓存及更新时间。
4. 读取判断所需的小型字段投影即可，不加载正文和收件人；SQL 不更新它们，也不删除重建收件人。
5. 在同一事务内读取有效本地 mutation，保持“远端真实观测 + 有效本地意图覆盖展示”的现有规则。远端 Deleted FLAG 仍不能直接转成位置移出或本地删除。
6. 比较合成后的持久字段；观测和展示均无变化时返回未变，不写 local_updated_at、不重算投影、不添加此项 ChangeSet。
7. 实际有变化时返回 MessageId、SessionId 和必要的变化信息。每批将受影响 SessionId 去重后重算一次投影；继续使用具体事务和已有 recompute_projection，不新增投影调度框架。
8. 一个批次内先完成数据更新，再计算该批最终投影，commit 成功后才交付变更摘要。

目标有效性必须与字段更新一起落地，不能仅依赖网络返回后查询到的“当前位置”：

- 请求发起前，在同一数据库快照中捕获 AccountId、MessageId、FolderId、RemoteKey、位置修订、绑定修订和 generation，并携带 Task 10 的本地观测序号。只读取这些必要元数据，不读取正文或收件人。
- 提交事务中重新检查仍登录、收信协议匹配、文件夹未退役、generation 与绑定修订一致、原 Message 的位置为 Present，且固定位置和位置修订一致。对已知邮件的字段 UPDATE 必须用原 MessageId 与预期修订作条件，不按晚到时的查询结果重新定位目标。
- 同一事务内，先按 Task 10 的观测序号规则确认该读取未早于较新的远端写确认，再执行限定字段 UPDATE。该校验与 UPDATE 不得分成两个事务；SQL 同时带必要身份/修订条件，检查影响行数，不满足条件的旧观测直接丢弃、等待后续正常核对，不重定向到新目标。
- mutation 展示覆盖使用提交时仍有效、仍指向该固定位置/修订的最新意图，复用现有 get_effective/validate_target 的条件语义和 Task 10 的版本保护；不能把任意活跃 mutation 都当作覆盖来源。
- 本轮新下载的 Upsert 没有既有 MessageId/位置修订时，按既有完整快照路径的文件夹绑定、generation 和 Task 10 观测保护提交；不为它制造零修订的 flags-only 目标。
- 同目标但较新 mutation 已确认、原 mutation 行已删除时，旧读取也必须被拒绝；不得仅用“当前无 pending mutation”判断它新鲜。使用 Task 10 已确认的本地观测序号，不另加一套时间戳或观测版本框架。

unknown → 明确 false 即使没有改变展示，也是真实观测的持久化变化，不能被当成完全无变化。是否需要刷新 UI 按对查询结果的实际影响决定，不丢弃该观测。

### 3.4 范围与约束

- 不在本项增加 CONDSTORE/QRESYNC 或更换 IMAP 库。
- 不通过本项重写 mutation 认领、lease 或远端顺序；这些仍归 Task 10。
- Task 10 的观测序号与较新确认保护尚未实施。S-01 可先准备字段级仓储函数，但替换生产入口前，必须接通上述修订条件和 Task 10 防晚到契约并通过交错测试；不能先启用较弱入口，再将安全保护留作后续任务。
- 批次内 Session 去重与 Task 13 的批次返回边界衔接，不把整个账号所有文件夹合成一个事务。

### 3.5 验收

- FLAGS 未变化：没有邮件/收件人 UPDATE/DELETE/INSERT，没有无意义的 ChangeSet。
- FLAGS 改变：正文、标题、收件人、Session、位置和修订保持不变。
- 未返回 FLAGS 不清除观测；显式 FLAGS () 正确清除已观测标志。
- 有效本地已读意图仍覆盖展示，远端观测仍独立保存；无效或已终止意图不继续覆盖。
- 发起读取后位置 Missing→Present、绑定更换、目录退役重建或 UIDVALIDITY 改变，旧 FLAGS 不更新原目标或任何新目标；不产生对应投影写入和 ChangeSet。
- 同位置的较新 mutation 已确认且 pending 行已删除后，旧 FLAGS 仍被 Task 10 的观测序号拒绝；之后新发起的有效观测可正常反映外部客户端修改。
- 新 Upsert 已带同次观测时，只应用一次；普通 flags-only 路径仍正确更新。
- 同一批多封邮件属于同一 Session，最终未读数及预览正确；投影只需按受影响 Session 重算。
- 事务失败时邮件、投影和摘要均不伪装成功。
- 用数据库语句计数或受控追踪确认写入范围，不只检查最终值相同。

## 4. S-02：收敛 IMAP 同步进度，删除旧水位和兼容格式

### 4.1 原来的逻辑

主要位置：

- `domain/services/imap_sync_policy.rs`
- `infrastructure/imap/sync.rs::{FolderSyncResult, sync_folder}`
- `infrastructure/mail/cursor.rs`
- `application/use_cases/sync_use_case.rs::{has_pending_imap_history, sync_imap_mail}`

当前每轮用远端 UID 集合与本地已下载 UID 求差集，选一页下载；high/low 已不用于排除下载候选。

但同时仍执行：

1. 从已下载集合计算最大 UID，作为 last_uid/high_uid。
2. 计算未下载 UID 的数字边界 low_uid，以 1 表示完成。
3. 将 UIDVALIDITY 编码到 sync_cursor，将 high/low 编码到 page_cursor。
4. 另外把 UIDVALIDITY 保存到 generation。
5. watcher 解析这些游标，只判断 low_uid 是否等于 1 来决定是否继续。
6. 保留 high-only 旧格式、缺失 low 的回退、backfill_low 和 parse_last_uid。backfill_low 仅被测试调用，parse_last_uid 没有生产调用。

### 4.2 原因与影响

下载算法已从“按水位推进”变为“按实际差集恢复”，但进度模型仍保留原算法的形状。

- high 数值不再承担实际调度作用，却增加计算、序列化、解析和测试。
- 业务实际需要判断是否继续下载，却要绕经 UID 边界和 0/1 哨兵值。
- 同一 generation 有两份表达，需要额外维护一致性。
- 兼容旧游标违反未上线 V1 不保留历史兼容双轨的约束。
- 原拟增加的 has_pending_downloads 与 Task 13 权威候选的未完成状态重复；仅看候选为空又不能区别“还没扫描”和“已扫描且为空”。需要明确扫描事实，不能再加一份可从候选推导的完成布尔值。

### 4.3 拟修复的逻辑

**唯一进度事实来源是 Task 13 的持久候选与现有文件夹同步状态，不新增持久化 has_pending_downloads，也不创建临时进度结构。** 当前源码没有候选表，因此 S-02 与 Task 13 同批实施；Task 13 未落地前保持本项待实施，不单独切换 watcher 到一套不存在的数据源。

1. 保留 UID SEARCH ALL 与当前代、有效本地已持久化位置集合求差集的算法。Missing 位置不能当已下载；Invalidated 旧代和退役绑定不恢复。差集按 Task 13 的 record_discovered 持久化为候选，失败项继续由同一候选行表达重试事实。
2. generation 仍是唯一代次事实，不再复制到 IMAP sync_cursor。非空表示当前代完整 UID 扫描及全部发现候选已持久化；仅 SELECT 成功或部分候选提交不得建立扫描完成事实。
3. 已核对当前源码：sync_use_case.rs::merge_folder_progress 每批成功更新 synced_at；useSyncStatus.ts、useSettings.ts 和设置页也用它判断成功状态。因此保留 synced_at 的最近成功批次提交时间语义，失败不推进。新增当前代 initial_sync_completed_at 表达首次历史同步完成事实，不将 synced_at 是否为空作为完成判据。后续增量积压不清空 initial_sync_completed_at；它不是 pending 缓存。Graph 保留现有分页及时间语义。
4. 候选状态、next_attempt_at 和已落库内容表达下载结果。首次完整扫描已提交且当前代全部候选已下载或经权威核对不再存在时，在最终有界事务内设置 initial_sync_completed_at；首次空扫描可以直接设置。消息/附件引用、候选完成、投影及必要时间更新原子提交；冷却或失败候选不得计为完成，状态含义沿用 Task 13。
5. IMAP 的 sync_cursor/page_cursor 均为空；删除 high_uid/last_uid/low_uid、数字哨兵、high-only 格式、backfill_low、parse_last_uid、旧格式兼容与对应测试。V1 重建开发数据，不读回旧游标。Graph 保留真实分页游标。
6. UIDVALIDITY 改变时按现有身份规则隔离旧代消息/任务，Task 13 invalidate_generation 停用旧候选。新代扫描完成时切换 generation 并清空旧代 initial_sync_completed_at；无候选时可直接设置新代完成时间。synced_at 按现有代次重置规则处理。扫描失败不得提交新代扫描完成事实，旧快照仍须被代次校验拒绝。
7. 同一读快照查询有效绑定/generation 与候选；已扫描、初始未完成却无未完成候选的异常状态，应报告并经正常完整核对恢复，不凭空候选静默补报完成。

首次同步判定如下。表中是已有事实的解释，不新增四态状态机或持久布尔值：

| 情况 | 权威事实与调度 |
|---|---|
| 首次同步尚未扫描 | generation 为空；即使无候选也必须完整扫描，不宣称完成 |
| 首次扫描已完成、无待下载邮件 | 最终扫描事务提交 generation，并在确认无未完成候选后写 initial_sync_completed_at；该提交即完成初始同步 |
| 历史邮件仍在分批下载 | generation 非空、initial_sync_completed_at 为空，当前代有未完成候选；按到期时间继续或等待 |
| 历史同步已完成，进入正常增量同步 | initial_sync_completed_at 非空；新增候选由同一候选表处理，不能将正常增量积压重新解释成首次历史同步 |

第二行是进入第四行的提交时刻，两者无需不同的持久状态。扫描是否发生、是否仍有候选、候选是否到期各有实际判据；不重复存储可推导的“完成”结论。generation、synced_at 和 initial_sync_completed_at 对 application 保持协议中性，UIDVALIDITY/RemoteKey 的解码仅在 infrastructure。

### 4.4 与 Task 13 的边界

Task 13 负责候选落库、逐批控制流和退避；本项只收敛其进度来源。完整 UID 扫描在写事务外执行，发现候选按 Task 13 的有界批次幂等落库，不将全部候选或网络等待放入一个事务。各发现批次携带目标代次与预期绑定并在提交时重验；全部发现批次成功后，最终小事务重验绑定/代次并提交 generation 扫描完成事实。完成标记发布前不消费该目标代的部分发现候选，也不判断完成。中断后重新完整扫描并幂等补录，仍使用同一候选表，不增加扫描注册表；旧快照不能绕过现有代次/修订保护。

消息下载仍一夹一批提交，不与完整扫描合成大事务。所有已知候选已记录不等于内容已经全部下载。

- 有可立即下载的候选：主动继续。
- 仅剩冷却候选：允许 IDLE/有限等待，到期再重试。
- 已完成扫描且无待下载候选：按常规 IDLE/周期核对；尚未扫描时先扫描。

初始扫描产生的候选、成功下载、冷却中的失败候选均使用 Task 13 的同一张表和已有函数。不新增完成计数、全局扫描注册表或第二张进度表。

调度进度不替代通知分类。本项保持基线 ChangeOrigin/new_incoming_ids 的输入输出规则：原 IMAP 的 sync_cursor.is_none() 首次批次判定迁移为“本批发起时尚无已提交 generation”，不能因 initial_sync_completed_at 仍为空就将所有后续批次重新判为 InitialSync，也不能因候选为空改变 origin。已有历史导入不通知、真正增量来信才通知的业务规则不变；基线后续历史批次被标为 IncrementalSync 的分类缺口仍须由 Task 05/13 明确处理，不在本项用新进度字段隐式改写算法。该缺口作为 Task 05/13 的明确待办，V1 实际使用前必须解决并验证历史补拉不通知、真正增量来信才通知，不宣称本项已解决通知分类。

### 4.5 验收

- 首次多批、UID 不连续、中间缺正文、下载后重启，都按实际持久化结果恢复。
- 新文件夹候选为空但 generation 为空时仍会扫描；首次空扫描在同一提交中记录 generation/initial_sync_completed_at，之后正常进入 IDLE，不反复当首次扫描。
- 首次多批未完成时 initial_sync_completed_at 保持空，synced_at 随成功批次更新；最后一批与候选完成、initial_sync_completed_at 同事务提交。冷却失败不能误报完成；历史完成后的增量候选不重置首次完成事实。
- 大邮箱候选发现按有界事务提交，最终扫描标记不重写全部候选；中途失败或崩溃后重扫幂等恢复，部分发现不冒充完整扫描。
- 空邮箱、UID 最大值和已删除 UID 不再需要数字哨兵特殊处理。
- generation 变化仍失效旧位置与旧任务，新代同 UID 不继承旧实体。
- 进度回滚不出现“未提交邮件已经完成”的状态。
- 同步代码不再读写旧 IMAP 水位格式，未新增持久 has_pending_downloads 或同义缓存；原生 Graph 分页/续传不受影响。
- 首次与后续同步分类可解释，历史补拉不因本次改动新增错误通知。
- 与 Task 13 一起验收：仅有退避候选不会形成两秒无限重试循环，扫描/候选/最终下载提交故障均不误报完成；Task 13 未实施时不启用此新入口。

## 5. S-03：统一 IMAP 连接参数与认证的解析入口

### 5.1 原来的逻辑

同步、目录发现、设置已读、删除、watcher 都自行进行以下操作：

```text
读取 AccountMailTransport
  → 分别取 host、port、TLS、username 等 Option
  → 自行处理默认值或缺失错误
  → 加载秘密
  → 匹配 auth_kind
  → 构造 ImapEndpoint 和 ImapAuth
```

其中同步/目录发现缺 username 报错；mutation 回退到账号邮箱；watcher 回退到秘密中保存的 username。TLS 也在多处自行回退为 Implicit。

### 5.2 原因与影响

同一个有效 IMAP 登录本应由一个确定的端点、用户名和密码引用构成，但 Option 平铺配置把“解释配置”的责任分散到了各个操作入口。

- 重复代码只是表面问题，实际问题是同一配置在不同入口含义不一致。
- 以后调整认证校验，需要修改所有入口，容易出现遗漏。
- 为获得 username 而额外读取 Account，扩大 mutation 对账号资料的依赖。
- 秘密与非秘密配置同时保存 username，形成两处来源。

### 5.3 拟修复的逻辑

直接接续工作区已有 Task 01，不重新构造另一套模型：

1. ReceiveConfig::Imap 中持有经校验的端点和 PasswordAuthConfig；用户名与凭据引用为必填。
2. SendConfig::Smtp 使用自己的经校验配置，可显式与收信共享凭据。
3. 用户表单不填用户名时，在输入入口一次性落实“默认使用邮箱”的规则，保存后不再由不同运行入口回退解释。
4. 密码原样传递，不 trim；用户名按入口明确规范化/校验，数据库读出同样不能制造无效配置。
5. 在已有 infrastructure/imap 模块增加一个普通函数，将有效 IMAP 配置与 AppPaths/凭据目录解析为所需 Endpoint/Auth；内部复用现有秘密加载和 session_login。
6. 同步、目录发现、mutation、watcher 调用同一函数，不各自拼装和降级默认值。
7. 普通函数不持有 AppState、不依赖 application DTO，也不负责账号 gate、后台调度或收信业务。
8. SMTP 复用相同的有效配置和凭据加载规则，但不为两种协议创建多层泛型连接工厂。

模型负责表达有效配置，infrastructure 函数负责把配置和受保护秘密接到协议库。两者职责不同，不能用“新增 helper”代替修正无效配置模型。

### 5.4 验收

- 各 IMAP 入口对同一配置生成相同用户名、端点和认证；没有入口特有的隐式回退。
- 非法/缺失端点、用户名、凭据引用在边界明确拒绝；损坏数据库配置不默认路由 Graph。
- 收发不同用户名/密码、显式共享引用都按 Task 01 通过。
- 密码首尾空格保持；TLS/STARTTLS、连接预算、取消退出的已有测试回归。
- 检索旧的平铺 Option 拼装路径和多套 username 来源，确认没有兼容旁路。

## 6. S-04：移除通用 OAuth2 的无效分支

### 6.1 原来的逻辑

账号输入校验拒绝非 Password，credentials::load 拒绝通用 OAuth2，session_login 也在 DNS 前拒绝 OAuth2。

但 MailSecret 仍含 access_token、refresh_token、expires_at_ms；application/runtime 仍构造 OAuth2 Auth，IMAP/SMTP 下层保留只通往拒绝或 unreachable! 的分支。

### 6.2 原因与影响

拒绝功能的入口已加上，原来试图支持该功能的数据形状和分支没有删除。这些类型允许表达无法执行的配置，维护者还需逐层证明它们永远不会到达。

Graph OAuth 与通用 IMAP/SMTP OAuth 生命周期不同，不能因为项目支持 Graph OAuth，就保留一套没有完整授权配置、刷新和撤销处理的通用分支。

### 6.3 拟修复的逻辑

1. 通用邮件秘密只包含实际需要的 password；username 归有效配置，不重复存于秘密。
2. 通用 IMAP/SMTP 协议认证类型只表达密码路径。若只剩一个变体且没有实际分支意义，使用简单结构即可，不强留单变体枚举。
3. 删除通用 OAuth2 输入字段、组装分支、unreachable! 和仅为这些路径存在的转换/测试。
4. 输入未知认证类型或旧参数不能被静默当作密码配置接受；明确拒绝非法输入，不保留旧 DTO 兼容形状。
5. 保留 Graph TokenCache、刷新令牌、到期时间和真实 OAuth 流程。
6. 删除共享 MailAuthKind 等类型前检查全部调用点；仍有真实用途的类型不为清理一个路径而误删。

本项与 S-03/Task 01 一起实施，避免先抽取包含无效分支的 helper，再删除一遍。

### 6.4 验收

- 通用 OAuth2 输入在副作用前失败：无新凭据、无数据库配置、无 DNS/认证请求。
- 通用运行路径不再包含 OAuth2 Auth、刷新字段或为其保留的 unreachable!。
- Graph 登录、刷新、随机引用切换保持工作；不能用全局删除 OAuth2 字符串作为验收标准。
- 前端、Port、Adapter、IPC 的新参数形状一致；无旧字段兼容读取链。

## 7. S-05：缩小凭据全局锁范围，保留刷新与回收安全

### 7.1 原来的逻辑

`infrastructure/mail/credentials.rs::lock` 锁定整个 credentials_dir 下的 mail-config.lock，使用 try_lock，竞争时立即返回 Conflict。

`graph/auth.rs::get_access_token` 在令牌过期时：

```text
取得全局配置锁
  → 重新加载该引用的缓存
  → 远端 HTTP 刷新令牌，await 时持续持有全局锁
  → 原子保存刷新结果
  → 释放全局锁
```

账号配置切换、退出和启动孤儿恢复也使用同一把锁。

### 7.2 原因与影响

全局锁原本要保护“暂存 → 引用切换 → 回收”与刷新回写的一致性，目标是必要的；但把远端等待也放进全局临界区，将互不共享凭据的账号耦合起来。

账号 A 刷新缓慢时，账号 B 的保存、退出或刷新可能直接 Conflict。重试增加了用户和调度器负担，但没有处理真正需要互斥的资源边界。

另一个缺口是：配置已切换后，旧秘密可能因 S-06 所述删除失败留在磁盘。文件存在只能证明有残留内容，不能证明原账号仍登录、仍通过原协议使用该引用，因此不能作为刷新回写的有效性判据。

不能直接把全局锁删除，否则可能重新出现重复刷新、已删除引用被刷新线程写回，以及回收正在暂存的秘密等竞态。

### 7.3 拟修复的逻辑

只保留两个有实际职责的锁范围，使用普通模块函数和现有文件锁能力：

| 范围 | 保护什么 | 是否覆盖远端刷新请求 |
|---|---|---|
| 单一凭据引用的刷新锁 | 同一引用不同时刷新，避免 refresh token 轮换互相覆盖 | 是，只影响该引用 |
| 现有目录级配置锁 | 暂存、配置引用切换、孤儿回收，以及刷新结果最终回写前的有效性检查 | 否 |

刷新流程：

1. 调用方固定原 AccountId、Graph 使用侧（收信/联系人沿用当前接收配置路由，发信使用发送配置）、命名空间及 CredentialRef。infrastructure 通过显式数据库资源和现有仓储模块函数核实当前配置，不依赖 application、AppState 或回调接口；仅传缓存文件路径不再足以完成校验。
2. 取得固定引用的刷新锁；等待过程有预算且可取消，不在 async 执行器线程上执行阻塞式 File::lock。再短暂取得全局配置锁，用新的数据库读快照核实账号仍登录、该使用侧仍为 Graph 且仍引用原 CredentialRef，然后重新读缓存。无效则停止；已有新鲜令牌则使用它，不刷新。释放全局锁后才允许网络请求。
3. 保持引用刷新锁，不持有全局配置锁，执行受超时和取消控制的远端刷新。
4. 响应成功后，在原操作预算内重新取得全局配置锁；重新检查取消/超时，用新的数据库读快照再次核实第 2 步的账号登录态、使用侧、协议和固定引用。不能沿用网络前的查询结果或长期读事务快照。
5. 配置已切换/账号已退出/查询失败时，不写回、不返回该迟到刷新 token、不改为使用另一个引用。即使原文件仍在或该引用仍被另一个使用侧引用，也不能代替原使用侧有效性检查。有效性确认后重新读取并校验同一缓存，再原子写回；有效配置所需文件缺失、解密失败或安全存储不可用按认证/存储错误报告，不创建新文件来掩盖故障。
6. 全局配置锁覆盖最终数据库校验到缓存原子写入的整个区间；检查与写入之间不得释放锁。结束后 RAII 释放两把锁。取消在提交检查前被观察到则不写入；若在原子写入已完成之后到达，不承诺回滚已发生的安全缓存更新，后续退出/切换仍按同一全局锁串行处理。

账号切换、退出、孤儿回收继续由现有全局配置锁保护，不等待引用刷新锁。它们可以在 HTTP 请求期间切换/失效引用并尝试删除旧文件；不论删除成功与否，迟到刷新都必须通过当前数据库关系判断失效。反过来，刷新若先完成最终校验与原子写回，切换操作随后才取得锁，并按正常流程使旧引用失效和回收。

复用 mail_transports 的配置读取及 is_credential_referenced 等模块函数，不新增引用注册表。两种查询语义必须区分：回收检查“任一保留的收/发配置是否引用该秘密”，应保守保留；刷新检查“原账号当前使用侧是否仍登录且使用该 Graph 引用”。现有 is_credential_referenced 本身不校验登录态或使用侧，不能单独作为刷新许可。

随机引用不可复用，命名空间不可偷偷改变；切换后不得把旧 CredentialRef 重新绑定为新凭据。数据库核实失败不等于引用已失效/无引用，既不回写也不删除。上述检查属于最终回写入口的必要条件，不新增版本控制框架。

### 7.4 锁顺序、取消与文件约束

- 刷新允许“引用刷新锁 → 全局配置锁”；禁止“全局配置锁 → 等待引用刷新锁”，避免环形等待。
- 配置暂存仍需从写新秘密到 SQL 切换/失败清理受全局锁保护，避免恢复器误删暂存文件。这里有本地数据库 await，不等于允许把浏览器认证或 HTTP 刷新放进全局锁。
- 引用锁键应包含命名空间与 CredentialRef，按已有安全路径编码处理，不直接拼接未校验字符串。
- 引用锁文件与 .secret 文件分开，孤儿扫描不把锁文件当秘密；不要在可能仍有等待者时删除/重建锁文件，避免同一引用出现两把物理锁。
- 同一引用的竞争可以使用有界、可取消的 try_lock 重试；不新增锁注册服务、后台清理线程或持久任务表。
- 引用锁和全局锁的等待均有界、可取消，最终校验包含原操作状态；已观察到取消/超时后不再开始回写。RAII 释放锁；原子写入前后的取消边界按 §7.3 处理。当前调用方本身没有统一取消参数的地方，接续已有 MailOperation/Task 04 的契约，不能再创建平行的取消体系。
- 不承诺已读取到内存的旧 access token 会被本地退出立刻从远端撤销；共同账号生命周期和远端 revoke 不属于本项。

### 7.5 验收

- A 的刷新响应故意阻塞时，B 的配置切换和令牌刷新不因 A 持有目录全局锁而失败。
- 同一引用并发刷新只有一个实际请求，等待方重新读取最新 token；验证 refresh token 轮换。
- 刷新期间退出或切换并删除旧引用，迟到响应不能重建旧文件。
- 切换已提交但旧秘密故意删除失败、原文件仍在时，迟到响应不改写该孤儿，不返回旧 token 作为当前配置令牌；收/发共享时，仅另一侧仍引用也不能使已切换的原使用侧通过校验。
- 最终数据库引用核实失败、有效秘密损坏或缺失时不回写、不转用新引用，也不将错误当作孤儿删除失败忽略。
- 启动恢复与暂存配置交错，不误删将被提交的新引用。
- 验证刷新先写回/切换先提交两个顺序，以及“引用锁→全局锁”交错；无路径持有全局锁等待引用锁，无锁顺序死锁。
- 超时、取消、HTTP 拒绝、原子写失败后锁可再次获取；没有新秘密或 token 出现在日志。
- 必须保留跨进程语义，使用两个实际进程验证引用锁与配置锁竞争；单进程测试不能替代该结论。

## 8. S-06：按实际提交结果返回保存成功，回收失败单独记录

### 8.1 原来的逻辑

IMAP/SMTP upsert 与 Graph complete_sign_in 都是：

```text
保存新凭据
  → SQL 事务提交账号及新引用
  → 删除旧凭据
  → 删除成功才返回 Account
  → 删除失败返回 Err，尽管账号配置已提交
```

已有 recover_credentials 能在启动时扫描无配置引用的 mail/graph 秘密，清理暂存或旧引用。

### 8.2 原因与影响

把“配置是否保存成功”与“历史凭据是否回收成功”合成一个失败结果，导致返回契约不能准确反映数据库事实。

- 前端拿不到成功 Account，可能不执行 afterAccountReady，账号列表、导航和文件夹设置入口与实际状态不一致。
- 用户重试会再次创建凭据和切换引用，增加无必要的状态变化。
- 调用者难以区分应重试配置，还是只需等待已有清理恢复。

回收失败仍需可观测，但不能通过谎报主操作失败实现。

若保存阶段将已确认孤儿的删除失败降为非致命，启动阶段却对同一文件删除失败直接退出，主操作虽成功、应用下次仍不可用。需要统一“已确认孤儿的独立删除失败”语义，不能只修改 upsert/sign_in 的返回分支。

### 8.3 拟修复的逻辑

本项保持现有 AccountPort 成功返回 Account 的契约，不为清理建立通用结果框架或新队列：

1. 参数、秘密写入、数据库事务在提交前失败，继续返回错误，按现有安全规则清理新引用。
2. commit 返回错误时，保留现有引用核实逻辑，不因“不确定是否提交”而误删可能已生效秘密，也不能擅自改报成功。
3. 已明确提交成功时，以 Account 作为主结果。旧凭据回收失败不再使用 `?` 覆盖成功结果。
4. 回收失败通过现有日志路径记录可定位的账号、阶段和错误类别，不记录密码、token、秘密内容；明确区分“配置已生效、回收未完成”。
5. 保留旧的未引用密文，由已有启动恢复继续尝试清理；独立孤儿删除失败的启动处理按 §8.4，不能在下次启动重新升级为全应用失败。不另建补偿任务表或自动重新提交账号配置。
6. 按新的收发独立配置检查所有有效引用：只有确实不再被任一收/发配置使用的旧秘密才能删除，共享引用只处理一次。
7. runtime 成功后照常通知 watcher，前端正常刷新账号；不能因非致命回收失败跳过这些成功路径。

本项的最小可观测要求是日志与已有启动恢复错误可查询/可诊断，不扩展 IPC 返回类型。只有在已确认提交成功、旧秘密已确认无引用后，删除操作的独立失败才降为非致命；引用查询失败时不删文件，记录核实失败，仍不把已提交保存改报回滚。下一次恢复必须重新核实，不能沿用“上次可能是孤儿”的猜测。若后续产品明确要求向用户展示清理警告，再为该具体需求设计提示，不在本项预建 warning 框架。

### 8.4 与退出及启动恢复的区别

退出时删除当前有效凭据失败，仍应明确报告，不能套用“保存成功后旧秘密清理非致命”的规则。本项不把实际退出失败改成成功。

当前源码的 recover_credentials 在单个 delete 失败时直接返回错误，setup 随之失败。本项必须同时修订该分支，复用原启动恢复入口，不新增清理服务或定时器：

1. 按现有全局配置锁完成引用核实与删除，防止引用检查后配置交错。先读出并校验所有保留收/发配置，按协议确认秘密命名空间并合并引用；共享引用只处理一次。保留配置仍指向的引用应保守保护，不能只因账号已退出就把它当作孤儿。
2. 启动恢复仅处理引用核实与孤儿回收，不遍历加载、解密或校验所有账号的有效秘密，不进行远端认证/刷新，也不为孤儿清理预先访问或创建系统密钥。受引用保护的秘密无需读取内容即可保留，删除已确认孤儿无需解密。
3. 无法取得必要锁、数据库引用查询/配置校验失败、目录无法可靠枚举，或恢复实际依赖的安全存储机制无法可靠工作时，返回明确错误，不将其解释为“无引用”，不删除待核实文件。不为账号凭据健康增加启动探测。
4. 只有在成功确认该命名空间下文件不被任何保留收/发配置引用后，才将它作为孤儿调用 delete。对此单个删除操作的权限/占用等失败记录阶段、错误类别及不含秘密的定位信息，继续处理其他已确认项，允许启动正常完成。文件已不存在按已有幂等删除规则处理。
5. 不因读取/解密未知文件失败而推定它是孤儿，也不需要为删除已确认孤儿解密其内容。引用核实必须先于删除；核实失败始终保留文件。
6. 已确认孤儿删除失败保留原文件，下一次已有启动恢复或正常配置变更确实涉及该引用时再按相同规则处理；不添加后台扫描、补偿队列或新调度时机。每次重新查询当前全部引用，不复用失效的孤儿判定。

必须缩小非致命范围到“已确认孤儿的独立删除失败”，不能通过将所有 Storage/InfraError 都改成日志实现。单个账号凭据缺失、解密失败、token 形状损坏或认证失败在账号使用时报告，并允许重新登录，不阻断整个应用启动或无关账号使用；数据库或安全存储机制本身无法可靠工作时仍明确报错，不生成替代密钥掩盖故障；退出当前有效凭据清理失败的既有安全语义保持不变。

### 8.5 验收

- 注入旧秘密删除失败：返回成功 Account，新配置和新引用可用，前端走成功流程，有明确回收日志。
- 解除删除故障后，已有 recover_credentials 清理孤儿但保留全部有效收/发引用。
- 保存成功后重启，令同一已确认孤儿持续不可删除：记录错误、其余账号仍能启动和使用；故障解除后下一次已有恢复成功回收。
- 单账号有效秘密缺失/损坏不因启动清理被主动读取或阻断启动；使用该账号时明确报告并允许重新登录，其他账号可使用。
- 数据库引用核实失败、目录无法可靠枚举或恢复实际依赖的安全存储机制不可用时仍明确报错，不删除未知文件，不能误入孤儿删除失败的非致命分支。
- 同步提交引用切换与启动回收交错，共享收/发或仅一侧保留的引用均不误删；有配置引用但已退出的账号不会仅因退出被当成孤儿。
- 新秘密保存失败、SQL 失败、COMMIT 失败仍返回错误；旧配置及秘密按原子切换契约保留。
- 同一引用被收/发共享或仍被有效配置引用时不删除。
- 退出删除当前凭据失败仍可见且可重试，不能显示已完整退出。
- 日志不泄露任何认证秘密。

## 9. S-07：完成 application 与 runtime 的职责边界

### 9.1 原来的逻辑

已提交基线中：

- account_use_case::clear_local_data 接收整个 AppState，直接使用数据库、草稿容器和 ChangeDispatcher。
- sync_use_case 接收 runtime::ChangeDispatcher，内部 commit 后分发并驱动聚合。
- 其他相关用例仍有 AppState、runtime 或 Tauri 任务启动依赖。
- runtime 已存在账号暂停、gate、watcher 与任务持有入口，但部分编排仍留在 application，依赖方向没有彻底收敛。

这主要是已确认架构约束尚未完成，不应为了修复而增加新的 UseCase trait 或事件层。

### 9.2 原因与影响

用例只需要具体资源和业务参数，却拿到整个运行时状态，导致：

- application 与 runtime 双向引用。
- 本地数据规则测试要构造不相关的 Tauri 资源。
- 生命周期、事件分发和业务事务难以各自说明完成边界。
- clear_local_data 数据库已提交后，若进程内草稿锁获取失败，会返回错误且跳过分发；再次出现“部分事实已完成，但调用只得到失败”的问题。
- 事件分发是非事务副作用；若未来边界调整把 emit 错误通过 `?` 传回主业务路径，会把已提交事实误报成数据库操作失败。当前 dispatcher 已记录 emit 错误而不拖垮写路径，这一正确语义必须保留，不能在移交 runtime 时丢失。

### 9.3 拟修复的逻辑

直接按 Task 04 实施，本文补充本次发现的具体边界：

1. runtime 保留 AppState、任务句柄、账号 gate、取消、暂停/恢复和 commit 后事件分发。
2. application 接收 SqlitePool、路径、操作控制及该用例必需数据，不接收 AppState/ChangeDispatcher，也不启动 Tauri 后台任务。
3. application 完成事务后返回必要业务结果和已提交 ChangeSet。失败事务不返回可分发摘要。
4. commit 成功后，主业务结果即按数据库真实状态返回成功；runtime 分发失败或其他非事务收尾失败，只记录对应阶段错误，不能转成“数据库操作失败/已回滚”，也不能自动重放原业务写入。保留现有 dispatcher 非致命 emit 语义，不新增通用结果框架。
5. 逐文件夹/逐批交付与部分成功的完整控制流归 Task 13，不为本项重新设计同步器。

提交与事件的具体边界：

| 时点/结果 | 对调用方与前端的语义 |
|---|---|
| commit 前失败，或尚未确认 commit 成功 | 返回对应错误，不伪造成功 ChangeSet；保留现有对提交不确定性的处理，不声称已回滚或擅自重试 |
| commit 已确认成功、事件发送成功 | 返回已提交业务结果，事件仅提示 UI 重查 SQLite |
| commit 已确认成功、事件发送失败 | 主业务仍成功；runtime 记录账号、操作/阶段和错误类别，保留可诊断信息，不能再用 `?` 覆盖成功结果 |
| commit 后分发前进程崩溃 | 不承诺内存事件送达；重新启动/进入页面时通过现有 Port 从 SQLite 读取真实状态 |

页面重新进入、应用启动时应重新读取数据库，不能永久依赖旧内存列表或某条必达事件；已有 Task 05 的版本补查、同快照查询和乱序保护继续由 Task 05 实施，不在 S-07 重建查询/事件通道。Task 13 每批提交后独立交付成功结果，后批失败或某批 emit 失败不抹去前批已提交事实。系统通知保持尽力而为，不新增 Outbox、持久事件总线、重发队列或补偿工作流。

clear_local_data 的最终修复安排在 Task 03 草稿持久化之后，使用以下确定的边界：

1. runtime 先进入已有账号屏障，停止并等待会写入该账号数据的任务退出。
2. application 在同一 SQLite 事务内清理本地聊天、同步和已持久化草稿，按 Task 03 的附件引用契约清除关联引用。
3. commit 成功后返回 account_cleared 摘要，runtime 分发；失败则整体回滚。
4. 附件实体文件的后续回收沿用 Task 03 已有机制，不把文件回收失败变成数据库清理未发生。

若 Task 03 尚未完成，可以先收敛其他用例的资源依赖，但本用例的完整事务修复保持待办。不为临时进程内草稿建立新的两阶段协议，也不持有 std::sync::MutexGuard 跨 async await。

### 9.4 验收

- application 不再导入 AppState、runtime、tauri::async_runtime 或 ChangeDispatcher。
- infrastructure 仍不反向依赖 application；domain 仍无 IO。
- commit 前失败无事件；commit 成功后的事实不因后续处理失败而丢失刷新摘要。
- 注入 emit 失败：SQLite 已提交值保留，主调用仍成功，runtime 有可诊断日志，无重复业务写入；数据库事务不被错误标为回滚。
- commit 后分发前终止进程，重启或重新进入页面可经 Port 查到真实数据库状态；不要求收到崩溃前内存事件。
- 清库失败保留草稿；清库成功正确清理该账号草稿且不误伤其他账号。
- 账号暂停、取消和 worker 收尾回归通过；旧线程未退出前不放行新任务。
- 不新增 trait 对象、接口层或平行分发通道。
