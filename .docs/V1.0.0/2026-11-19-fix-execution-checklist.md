## F01：贯穿账号取消，缩小执行单元

### 修改范围

- `src-tauri/src/runtime/send_worker.rs`
- `src-tauri/src/runtime/archive_worker.rs`
- `src-tauri/src/application/use_cases/outbound_use_case.rs`
- 实际发送及 APPEND 的 infrastructure 调用链。

### 必须实现

1. 优先将一次认领改为一项任务，使一次 permit、一次 operation 和一次尝试对应，避免为未执行批次增加复杂补偿。
2. worker 创建 operation，将其 clone 登记到 gate，并将同一控制对象传入用例和实际协议操作。仅新增参数但调用时另建 operation 不算完成。
3. 在开始远端写入前检查取消。SMTP、Graph 和 IMAP APPEND 都要检查实际执行路径，不能只接通其中一种。
4. 账号变更触发取消后，等待实际操作退出。阻塞线程仍在运行时不得释放 permit 或开始清理账号。
5. 按是否已经开始写入、是否取得接受证据收尾：未执行可安全恢复，明确成功保留成功，结果未知不自动重发。
6. 结果持久化及必要失败收尾完成后再释放 permit。数据库失败只重试本地记录，禁止重新执行网络写入；重试有界，失败报告清楚。

如果选择保留一次认领多项，必须额外证明：每项开始前检查取消，未执行的已认领任务不会遗留为 sending/appending，操作期限不会错误覆盖整个长批次。

### 必须验证

- 写入前取消：发送/APPEND 调用次数为 0。
- 操作阻塞中取消：实际连接或请求收到取消，账号变更等待真实操作退出。
- 存在多项到期任务：取消后没有后续任务开始写入。
- 写入后响应未知：持久化 uncertain，下一次 tick 不重发。
- 接受结果已取得、本地事务尚未提交：账号清理等待收尾，成功事实不被取消覆盖。

## F02：修正 APPEND 外层超时语义

### 修改范围

- `src-tauri/src/infrastructure/imap/client.rs` 的 `append_message_async` 及结果分类。
- `src-tauri/src/runtime/archive_worker.rs` 的结果持久化分支。
- 必要时调整 `src-tauri/src/infrastructure/mail/operation.rs`，但必须复核共享调用者。

### 必须实现

当前问题不只在 `session.append`：`run_blocking` 在超时/取消分支丢弃线程结果，返回通用 Network；worker 又按 retryable 安排下一次 APPEND。

1. 明确划分连接/登录、APPEND 写入及确认、连接清理三个阶段。
2. 连接或登录阶段失败且尚未 APPEND 时，允许按错误性质处理安全重试。
3. APPEND 开始后，外层超时、取消或线程异常若没有明确未接受证据，必须保留未知，不能直接走通用网络重试。
4. 已收到 APPEND 成功确认后，logout 失败或超时不得覆盖成功结果。
5. 仍要等待真实阻塞线程退出；不能通过提前返回来保留结果，却留下仍在写入的线程。
6. 不全局把 Network 改成 uncertain；只读同步等调用仍应保留各自错误语义。

### 必须验证

| 注入位置 | 预期 |
|---|---|
| 连接失败，未 APPEND | 可按临时错误安全重试 |
| 服务端保存 literal 后不回确认，外层超时 | uncertain，不再次 APPEND |
| APPEND 成功后 logout 阻塞 | 保留成功，不再次 APPEND |
| APPEND 中取消 | 等待退出，按实际证据保留成功或未知 |

测试必须经过异步包装及持久化分支；只调用 `classify_append_result` 不足以验收。

## F03：撤销猜测确认，保留明确的能力边界

### 修改范围

- `src-tauri/src/application/use_cases/sync_use_case.rs` 的 Sent 任务确认路径。
- `src-tauri/src/infrastructure/repository/archive_tasks.rs` 的 `confirm_by_internet_message_id`。
- `src-tauri/tests/end_to_end_acceptance.rs` 中固化 Message-ID 匹配的断言。
- 若实现确定位置证据：相关适配器、最少必要存储和用例事务。

### 必须实现

1. 删除按同 Message-ID 自动把 waiting_server_copy/uncertain 任务改成 confirmed 的生产行为，不保留兼容别名或备用猜测路径。
2. 禁止通过添加主题、正文、时间等相似度条件继续猜测关联。
3. 如果具有 APPENDUID 等确定证据，由适配器转换为统一位置，再核对账号、文件夹、绑定修订、代次和远端键。
4. 遵循 Task 14 的首次绑定规则：确定目标尚不存在且原记录无位置时可首次绑定；位置已有实体时任务引用已有实体，不合并不同位置。
5. 无可靠证据时保持待核对。服务器已写入与本地位置已关联是不同事实；不得为了让任务结束而伪造 confirmed。
6. 有证据的关联与必要位置写入、账号版本更新放在同一事务，提交后发事件。

先移除错误确认即可消除误确认风险；如果可靠位置关联尚未实现，必须将归档完整能力保持为“部分完成”，明确记录限制，不得宣称 F03 所涉及的归档闭环全部验收。

### 必须验证

- 同账号 Sent 中另一位置具有同 Message-ID：任务不自动确认。
- 多个任务具有相同 Message-ID：不会一次全部关联同一实体。
- 确定证据对应旧绑定或旧代次：不能确认当前任务。
- 确定目标已存在：引用已有实体，不产生第二个同位置实体。
- 缺少证据：保持待核对且不重复 APPEND。

## F04：刷新真实发送状态区

### 修改范围

- `src/features/conversations/useMessages.ts`
- 账号版本补偿到当前会话刷新的实际接线；仅在需要时修改相关模块。

### 必须实现

1. `pendingSends` 目前不在普通消息 `entityCache` 中。发送事件必须直接更新或重查该列表，不能只更新 `messageState.items`。
2. 对当前会话的新入队、sending、accepted、failed、uncertain 和取消后的移除都有效。
3. 普通邮件列表为空、只有发送状态记录时也必须刷新；不能把“是否命中普通消息缓存”作为唯一处理条件。
4. 事件丢失后的账号版本补偿要实际到达当前发送状态区，而不只是刷新会话导航列表。
5. 与 F05 共用清晰的请求有效性规则，不增加高频轮询。

### 必须验证

- 当前会话持续打开，无其他同步事件，状态随发送结果更新。
- 新记录加入和取消记录移除正确。
- 丢弃一次发送事件，恢复焦点后由版本差异补偿刷新。
- 旧状态查询晚于新状态查询返回时，不回退到旧状态。

## F05：校验全部异步结果后再写入 UI

### 修改范围

- `src/features/conversations/useMessages.ts` 的 `loadInitial`。
- F04 新增或调整的局部刷新函数。

### 必须实现

1. 将 `listMessages` 和 `listPendingSends` 的结果先保存在局部变量中，查询完成后统一核对请求版本、账号、会话及 sessionVersion。
2. 核对通过后再写记录、缓存、游标及 hasMore；迟到结果不应部分写入。
3. 错误及 loading 状态同样只允许有效请求更新。
4. 同会话多次刷新也要防止乱序覆盖。只检查 sessionId 不够，必须保留请求新旧判断。
5. 可并行读取两个独立查询，但并行不能替代返回后的校验。

### 必须验证

- A 的待发送查询被延迟，B 已完成加载，再返回 A：B 数据和分页保持不变。
- 跨账号切换和取消选中会话：旧数据不会重新出现。
- 同会话新请求先返回、旧请求后返回：保留新结果。
- 旧请求失败：不覆盖新请求的错误或 loading 状态。
