## F01 · P1 · 将账号取消贯穿实际发送与归档操作

### 代码依据与影响

- `src-tauri/src/runtime/send_worker.rs:109` 创建 operation 并交给 gate；`run_attempt` 和 `execute_claimed_attempt` 不接收该对象。
- `src-tauri/src/runtime/archive_worker.rs:52` 存在相同问题；`infrastructure/imap/client.rs` 的 `append_message_async` 另外创建 operation。
- 两个 worker 一次最多认领 4 个任务，随后在同一 permit 内顺序执行；循环没有检查账号取消。

用户在第一项执行期间退出账号，gate 取消的对象无法影响真实网络操作，后续已认领任务仍可能继续发送或 APPEND。延长 permit 能阻止账号清理越过收尾，但不能替代取消接线。

### 最小修复方案

1. 复用现有 `MailOperation`，使 gate 登记的取消控制贯穿 worker、用例及协议调用；协议层不得另建与账号取消无关的控制对象。
2. 在远端操作开始前、每个后续任务开始前检查取消。明确区分尚未开始网络写入的任务和已经开始的任务。
3. 简化认领粒度优先考虑每次许可只认领一个任务；如保留批量认领，必须对剩余未执行任务进行条件收尾，不能把它们留在 sending/appending，也不能误记为已执行后结果未知。
4. 取消后等待实际异步操作或阻塞线程退出，再按已有协议证据记录 accepted、明确未接受或 uncertain。取消本身不证明远端未接受。
5. permit 持有到结果事务及必要失败收尾结束。数据库失败只能有界重试本地写入，不得重发远端操作；失败仍须保留安全恢复状态并报告。
6. 操作预算应与实际执行单元一致，避免批次共享一个已经耗尽的期限却继续启动后续任务。

不增加第二套 gate、锁或通用调度框架。

### 验收场景

- 在远端写入前取消：不发出发送或 APPEND 命令，任务按明确未执行收尾。
- 第一项阻塞时取消：实际网络操作收到取消，剩余任务不会开始远端写入。
- 写入后丢失确认再取消：记录 uncertain，后续 tick 不重发。
- 已取得接受确认后取消：保留接受事实，不因取消覆盖成失败或可重试。
- 网络已结束、结果提交前设置屏障：账号清理必须等待收尾；验证真实 worker 调用链，不能只测试 gate 本身。

## F02 · P1 · 保留 APPEND 在超时和连接收尾边界上的确定性

### 代码依据与影响

- `src-tauri/src/infrastructure/imap/client.rs:301` 用 `operation.run_blocking` 包裹 APPEND 和 logout。
- `src-tauri/src/infrastructure/mail/operation.rs` 的 `run_blocking_until` 在超时或取消时等待线程退出，但丢弃线程结果，返回 `InfraError::Network`。
- `src-tauri/src/runtime/archive_worker.rs:155` 将可重试的通用错误安排为稍后再次 APPEND。

服务器已经保存邮件，但最终响应或 logout 阻塞到外层超时，未知甚至成功的结果会被覆盖成可重试网络错误，导致重复副本。仅测试 `classify_append_result` 无法覆盖该路径。

### 最小修复方案

1. 保留建立连接、登录等 APPEND 前失败的明确未写入语义：临时错误可重试，认证或永久错误进入相应可处理状态。
2. APPEND 一旦开始，外层超时、取消、线程异常等不能只凭通用 `retryable` 决定重写；无法证明未接受时记 uncertain。
3. 将 APPEND 的确定结果与 logout/连接清理结果分开。已收到 APPEND 成功确认，就不能被 logout 失败覆盖。
4. 等待实际线程退出后，优先保留已经取得的确定结果；没有确定结果时保持未知。复用现有结果类型或增加最少的显式结果字段，不再依赖布尔值和通用错误猜测阶段。
5. 不全局改变只读操作的网络错误语义。若调整共享 operation 辅助函数，必须核对已有同步、mutation 调用者，确保取消仍等待真实线程退出。

### 验收场景

- 连接失败、未执行 APPEND：恢复后可以安全重试。
- 接收完整 literal 并保存后不返回确认，触发外层期限：任务 uncertain，后续不再次 APPEND。
- 已返回 APPEND 成功，但 logout 阻塞到超时：保留写入成功，不再次 APPEND。
- APPEND 执行期间取消：等待线程退出；已知成功保留成功，未知不重试。
- 测试必须经过 `append_message_async` 的外层控制和 worker 持久化分支，而不是只构造协议错误调用分类函数。

## F03 · P1 · 移除基于 Message-ID 的归档自动确认

### 代码依据与影响

`src-tauri/src/infrastructure/repository/archive_tasks.rs:203` 的 `confirm_by_internet_message_id` 将同账号、快照 Message-ID 匹配的所有 waiting_server_copy/uncertain 任务确认到同一个 message_id。

`sync_use_case.rs` 只检查远端邮件位于 Sent 且 Message-ID 非空，没有获得本次尝试与该位置之间的确定映射，也没有核对任务目标和绑定修订。Sent 中复制或导入的同 Message-ID 邮件可能误确认任务。

“某封邮件具有确定远端位置”与“该位置确定属于本次归档”是不同事实。未合并 Message 实体，也不代表任务关联符合身份约束。

### 最小修复方案

1. 删除生产链路按 Message-ID 自动确认任务的行为；不能以增加正文、时间、主题等相似度条件补救。
2. 有 APPENDUID 等确定证据时，在协议适配器中转换为统一位置；由用例按账号、文件夹、绑定修订、代次和远端键验证并完成关联。
3. 确定位置尚未同步到本地时，保留证据等待该位置入库；如果需要保存证据，只增加满足该流程所需的最少数据，不引入 Graph 专有业务身份。
4. 遵循 Task 14：有确定目标且原发送记录尚无位置时可首次绑定；目标位置已有实体时任务引用该实体，保留原无位置记录，不合并不同位置消息。
5. 缺少可靠关联证据时保持待核对。APPEND 已写入但未完成位置关联，与 APPEND 是否成功必须分开表达；不能为了任务收敛伪造确认。
6. 关联、必要的位置写入和账号版本在同一事务中提交，提交后分发变更。
7. 修改 `end_to_end_acceptance.rs` 中将同 Message-ID 匹配视为成功确认的测试，避免测试固化错误规则。

### 验收场景

- 同账号 Sent 存在同 Message-ID 的其他位置邮件：不能自动确认归档任务。
- 多个等待任务具有相同 Message-ID：不能一次全部确认到一个位置。
- 有确定位置证据：只关联对应任务；绑定修订或代次失效时拒绝旧证据。
- 目标位置已存在：引用已有实体，不创建重复实体，不合并不同位置。
- 缺少位置证据：保留待核对，不自动再次 APPEND；不同账号和位置仍保持独立。

## F04 · P2 · 发送事件必须更新发送状态区

### 代码依据与影响

`src/features/conversations/useMessages.ts:305` 的 `applySendStates` 只查询 `entityCache` 并更新 `messageState.items`。`pendingSends` 独立加载且未加入该缓存。user_action 分支调用该函数后直接返回，不重载发送状态区。

因此后端 accepted/failed/uncertain 事件到达时，无位置发送记录可能被直接跳过，界面一直保留旧的排队状态。

### 最小修复方案

1. 对影响当前会话的发送状态事件，直接刷新当前会话的 `pendingSends`，或更新其中匹配的记录；优先复用现有 Port。
2. 处理新入队、状态变化及取消后的移除，不能只更新已有普通消息。
3. 异步刷新采用与 F05 一致的请求有效性检查，防止迟到响应覆盖新状态。
4. 核对事件丢失后的账号版本补偿，确保补偿能刷新当前发送状态区，而不只是左侧会话列表。
5. 不新增高频轮询掩盖事件接线问题。

### 验收场景

- 保持同一会话打开，发送依次进入 queued、sending、accepted，状态及时更新。
- 分别覆盖 failed、uncertain 和 cancelled，不依赖其他邮件同步事件刷新。
- 当前普通消息列表为空、只有本地发送记录时，同样有效。
- 模拟事件丢失，焦点恢复后的版本补偿能更新发送状态区。

## F05 · P2 · 待发送查询返回后重新验证请求归属

### 代码依据与影响

`src/features/conversations/useMessages.ts:81` 在 `listMessages` 返回后检查版本，但新增的 `await listPendingSends` 返回后直接赋值，还继续写分页游标。

在 A 查询未返回时切换到 B，A 的迟到响应可能把 A 的发送记录显示到 B，并覆盖 B 的分页信息；切换账号也有相同风险。

### 最小修复方案

1. 将普通消息页与待发送列表先保存为局部结果，所有依赖查询完成后再检查请求版本、账号、会话和 sessionVersion。
2. 只有当前请求仍有效时才更新共享 UI 状态，包括记录、缓存、游标、hasMore 和错误状态。
3. 如并行读取两个独立查询，仍必须在共同完成后校验；并行本身不能解决竞态。
4. F04 新增的局部刷新也必须防止旧请求覆盖较新的查询结果，复用简单版本计数即可，不引入通用请求框架。

### 验收场景

- 延迟 A 的待发送查询，切换 B 并完成加载，再返回 A：B 的记录和分页信息不变。
- 跨账号切换、取消选中会话时，迟到响应不能重新显示旧数据。
- 同一会话连续两次刷新，旧响应最后返回：只保留较新结果。
