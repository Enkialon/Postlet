## R01 · P1 · Graph 发送响应丢失后会自动重发

**位置**：`src-tauri/src/application/use_cases/outbound_use_case.rs` 的 `execute_claimed_attempt` Graph 分支；`src-tauri/src/infrastructure/graph/mail.rs:302`；`src-tauri/src/runtime/send_worker.rs:247`。

**关联改动**：`5aa733b` 引入持久化发送队列和自动重试，将 Graph 发送错误接入通用可重试错误分支。

Graph `send_mail(...).send().await` 的网络错误经 `map_http_err` 转成 `InfraError::Network`，再经 `AppError::from` 转成 `retryable=true`。worker 对这类错误直接写 `Retryable`，没有区分请求未发出和服务器已接受但应答丢失。成功时虽返回 `SendStage::Data`，失败路径却完全绕过阶段状态机。

**触发与影响**：Graph 接受发信后，客户端收到响应前连接断开。任务自动重试，收件人可能收到重复邮件。这与 Task 08 的“无法证明未接受时进入 uncertain”冲突。

**最小修复方向**：Graph 适配器返回具有接受确定性的发送结果；请求发出后的未知结果转 `uncertain`，只有明确未接受的失败才自动重试。不要仅凭通用 `retryable` 决定重新发信。

**怎么改及为什么**：在 Graph 发信适配器内区分确定未发送、明确拒绝、已接受和结果未知，并复用现有发送结果/状态机传给 worker。认证取 token 失败等发信前错误与发信请求后的错误应分别处理。只有确定未接受且允许重试的情况进入 retryable；不能为了统一接口把阶段证据丢掉。原因是发送属于有副作用的远端写入，连接失败不等于邮件未发出；全局修改 `AppError::Network` 会误伤只读请求，应限制在发信语义内。

**回归场景**：模拟发送请求被接收后丢弃响应，断言任务为 `uncertain`，后续 tick 不再调用发送接口。

## R02 · P1 · APPEND 将断线误判为拒绝，可能重复保存 Sent 副本

**位置**：`src-tauri/src/infrastructure/imap/client.rs:263–270`；`src-tauri/src/runtime/archive_worker.rs:125–133`。

**关联改动**：`de287d3`。

`append_message` 将 `session.append` 的所有错误转换为 `Ok(false)`，包括 I/O 错误。上层将 `Some(false)` 解释成“APPEND 被拒绝”，安排 60 秒后重试。适配器外层的 `Err(_) => Ok(None)` 无法接住已被吞成 `Ok(false)` 的 APPEND 错误。

**触发与影响**：服务器已写入 MIME，但最终确认响应丢失，客户端重复 APPEND，Sent 出现多个副本。此问题位于客户端归档分支；当前默认策略未接通及目标文件夹错误会遮挡它，修复 R03/R04 时必须同时处理。

**最小修复方向**：保留确定拒绝与结果未知的区别；最终响应未知记为 `uncertain`，不自动重复 APPEND。

**怎么改及为什么**：修改 IMAP APPEND 适配器的结果转换，明确的服务器拒绝与 I/O/响应解析不确定分别返回；worker 根据确定性以及拒绝是否临时决定失败、退避或 uncertain。不要继续用 `Err(_) => Ok(false)` 丢失信息。因为服务器保存和客户端收到确认不是同一件事，必须先保留协议事实才能正确重试。确定的永久配置错误也不应每分钟盲目重试。

**回归场景**：假 IMAP 服务端接收完整 literal 并保存邮件，随后断开而不返回 tagged OK；断言后续不会再次 APPEND。

## R03 · P1 · IMAP 归档把本地 FolderId 当作服务器邮箱名

**位置**：`src-tauri/src/runtime/send_worker.rs:85–115`；`src-tauri/src/runtime/archive_worker.rs:204–215`；`src-tauri/src/infrastructure/repository/folder_states.rs:134–135`。

**关联改动**：`de287d3`，与 `0c537e9` 已建立的本地文件夹身份模型接线不一致。

归档入队查询的是本地 `folder_id`；文件夹发现为它生成 UUID。执行时却将 `target_folder_id.as_str()` 直接传给 IMAP APPEND，没有读取该文件夹的 `remote_binding`。同时入队将绑定修订固定写为 1，执行时也不核对 `target_binding_revision` 或是否退役。

**触发与影响**：归档策略设为 `client_append`，本地 Sent ID 为 UUID、服务器邮箱名为 `Sent` 时，实际发送 `APPEND <UUID>`。正常服务器会拒绝不存在的邮箱，副本无法归档并持续重试。

**最小修复方向**：保存实际绑定修订；执行时按账号和本地 FolderId 读取有效绑定，验证协议、修订和退役状态，再将 `remote_binding` 交给 IMAP。

**怎么改及为什么**：入队同时读取 Sent 的本地 ID 与真实 binding_revision，替换硬编码 1；执行前通过现有 folder_states 仓储解析绑定，不匹配时停止旧目标操作并返回可处理的配置状态。原因是本地 ID 保证应用内部身份，remote_binding 才是协议端点；两者分离是已有业务约束。不能把数据库 folder_id 改回邮箱名来掩盖错误，也不能在旧任务执行时悄悄改目标。

**回归场景**：本地 ID 使用 UUID、远端名称使用 `Sent Items`，断言线上命令使用后者；文件夹退役或修订改变时拒绝旧任务。

## R04 · P1 · 所有新账号的归档策略都停在不可配置状态

**位置**：`src-tauri/migrations/001_init.sql:467–468`；`src-tauri/src/runtime/send_worker.rs:68–83`；`src-tauri/src/domain/entities/archive_task.rs`。

**关联改动**：`de287d3`。

数据库默认 `sent_archive_policy='needs_configuration'`。该值是合法枚举，`ArchivePolicy::parse` 成功，因此不会执行 `unwrap_or_else(default_for(...))`。全仓库生产代码只有迁移定义和 worker 读取此字段，没有设置策略的账号写入、IPC 或 UI。`needs_configuration` 任务也不在归档 worker 的认领范围内。

**触发与影响**：通过现有流程新建账号并成功发送。归档任务一直是 `needs_configuration`，用户没有方式让它继续。尤其 SMTP 服务端不自动保存副本时，Sent 不会获得发送副本；Graph 即使自动保存，归档任务也无法进入等待确认流程。

**最小修复方向**：提供明确的策略确认和持久化入口，并处理已等待配置的任务。遵守 Task 14 对“未确认时不自动选择”的要求，不应仅按收信协议猜测 SMTP 服务器是否自动保存。

**怎么改及为什么**：复用账号设置 Port/Adapter、薄 IPC 与账号用例，提供服务器保存/客户端保存的明确配置；客户端保存需要同账号有效 Sent 目标。保存配置时，在事务内推进适用的 needs_configuration 任务并增加账号版本；已经 uncertain 的任务不能借配置变化重置为可重试。Graph 使用明确的发送保存行为作为证据，SMTP 是否自动保存不能由邮箱品牌或收信协议推出。这样既补齐可用入口，又避免“默认启用 APPEND”制造重复副本。

**回归场景**：从真实账号创建入口走完整流程，确认策略后发送；断言 SMTP 客户端保存进入 `append_pending`，服务器保存进入 `waiting_server_copy`，待配置任务可以继续。

## R05 · P1 · 发送接受确认和归档入队没有事务保护

**位置**：`src-tauri/src/runtime/send_worker.rs:214–239`；`src-tauri/src/infrastructure/repository/send_tasks.rs:119–160`。

**关联改动**：`de287d3`。

worker 使用 `db.acquire()` 获得普通连接，先 `record_result(Accepted)`，再 `enqueue_archive`。没有 `db.begin()`，两次写入独立提交，代码中的“同事务”注释不成立。归档入队失败后只向调用方返回错误，已接受任务不再被发送队列认领，启动恢复也不会为其补建归档任务。

**触发与影响**：发送已接受，第一条 UPDATE 成功，第二条 INSERT 失败或两者之间进程退出。任务永久保留 accepted，却没有归档任务；客户端保存策略下无法产生 Sent 副本。

**最小修复方向**：接受确认、归档入队及版本变更放入显式事务；网络已成功而本地提交失败时，只重试本地确认，不能重新发送邮件。

**怎么改及为什么**：由 application 中的具体用例函数持有 SqlitePool 并管理事务，条件更新仍匹配 attempt/content_version/claim_token；仅当本次确认生效时创建对应归档任务并更新版本，提交后再分发事件。worker 保留已获得的接受结果，本地失败只重试该确认步骤。事务解决本地半写入，不可能让远端发送与 SQLite 原子提交；若进程在接受证据持久化前退出，恢复仍必须保守为 uncertain，不能承诺自动找回全部事实。无需增加事务管理 trait 或分布式事务层。

**回归场景**：对归档 INSERT 注入失败，确认不会出现已提交 accepted 但缺失归档任务的半状态；恢复过程不再调用网络发送。

## R06 · P1 · 发送与归档在结果落库前释放账号 permit

**位置**：`src-tauri/src/runtime/send_worker.rs:210–214`；`src-tauri/src/runtime/archive_worker.rs:105–108`；`src-tauri/src/runtime/mail_sync_gate.rs:73–103`。

**关联改动**：`5aa733b`、`de287d3`，并影响 `40f012c` 对账号清理屏障的保证。

两个 worker 都在网络调用返回后立即 `drop(permit)`，随后才获取数据库连接、记录结果和创建归档任务。`pause_and_wait` 只等待 gate 的 inflight 项消失，因而账号清理/退出可以先于这些收尾写入开始。

**触发与影响**：服务器确认成功后阻塞 worker 的数据库连接获取，同时触发账号清理。清理可删除任务/快照，随后旧 worker 更新不到结果；切换配置时，也可能让旧发送结果按新策略创建归档任务。账号变更返回并不代表旧任务已完成持久化收尾。

**最小修复方向**：permit 覆盖一次尝试的结果落库、归档入队和必要失败收尾，在所有收尾完成后释放。按 Task 08/14 要求，在取得 permit 后再认领任务。

**怎么改及为什么**：将顺序调整为取得账号许可→认领→执行→记录确定结果或不确定结果→提交→释放许可；复用现有 gate，检查提前返回与取消分支。收尾写入失败时进行有界本地重试，保留安全恢复状态并报告失败，不能永久持锁，也不能声称已经可靠落库。原因是账号清理需要等待完整工作单元，网络结束并不是任务结束。单纯把清理延迟几秒或增加一把锁不能保证这个顺序。

**回归场景**：网络返回后、本地提交前设置屏障；并发清理账号，断言清理必须等待结果记录完成。

## R07 · P1 · 下载候选退避未接入同步，整页坏信会饿死旧邮件

**位置**：`src-tauri/src/infrastructure/imap/sync.rs:71–73`；`src-tauri/src/application/use_cases/sync_use_case.rs:385–399`；`src-tauri/src/infrastructure/repository/download_candidates.rs:147–172`。

**关联改动**：`0b41ca7` 的最新优先差集选择，以及 `cdeac0b` 未完成接线的退避实现；`8969983` 未修复此路径。

实际下载始终调用 `missing_imap_page(remote, known, 200)`，不读取候选表及 `next_attempt_at`。`record_discovered`、`list_due`、`mark_downloaded` 没有生产调用方；唯一接入的 `record_failure` 只是 UPDATE，不会创建不存在的候选记录。因此失败不仅不会冷却，通常连失败记录也没有落下。

**触发与影响**：最新 200 个 UID 都无法读取或解析，而更旧邮件正常。每轮仍选相同 200 个失败 UID，更旧邮件永远没有机会下载，历史补齐持续重试。少量坏信也会在每轮重复抓取，违背退避约定。

**回归场景**：准备 201 封邮件，最新 200 封稳定失败、最旧一封正常；下一轮应跳过冷却 UID 并下载最旧邮件，候选表应保存失败次数和到期时间。

## R08 · P2 · 协议层仍先收齐全部文件夹，后一夹失败会丢弃前面结果

**位置**：`src-tauri/src/infrastructure/imap/session_ops.rs:33–38`；`src-tauri/src/application/use_cases/sync_use_case.rs:317–340`。

**关联改动**：`cdeac0b` 宣称完成逐夹提交，但只拆分了拿到整个 batch 后的数据库事务，未拆协议执行流程。属于本轮修复未闭环的问题。

`sync_account_blocking` 依次抓取所有文件夹，用 `?` 传播任一夹的错误，最后才返回 `Vec<FolderSyncResult>`。application 必须等待它整体成功，才开始逐夹提交。

**触发与影响**：A、B 夹已抓取成功，C 夹 UID SEARCH、正文 FETCH 或 FLAGS FETCH 失败，整个函数返回 Err，A/B 尚未提交的结果被丢弃。持续坏夹会反复阻断其他夹的进度。

**最新提交复核**：`8969983` 已将 SELECT 失败和缺失 UIDVALIDITY 转成夹级结果，因此这两种具体触发条件已修复，不再列为当前缺陷。SEARCH/FETCH 错误及中途操作超时仍通过 `?` 退出，批次交付结构未改变。

**最小修复方向**：每个文件夹批次完成后就提交并交付 ChangeSet，再继续下一夹；可保留连接复用，但不能等待所有夹成功后才落库。

**怎么改及为什么**：使现有协议执行流程能够按夹/批交付结果，由 application 提交后让 runtime 立即分发；下一夹失败只影响其自身未提交批次。连接已不可用时可以停止后续抓取，但不能丢弃已完成并提交的结果；本批失败不得推进游标。先选择最简单的单批调用结构，有必要时再保留连接复用，不为此创建通用消息总线。原因是只有提前提交才能保护前面成果，给原有整个批次外面再套错误捕获仍然太晚。

**回归场景**：第三夹在 FLAGS FETCH 返回错误，断言前两夹消息已持久化、变更事件已交付，第三夹保留原游标。

## R09 · P2 · 发送状态改变不发有效事件，也不增加账号版本

**位置**：`src-tauri/src/runtime/send_worker.rs:221–244、259–275`；`src-tauri/src/runtime/change_dispatcher.rs:23–26`；`src-tauri/src/application/dto/change_set.rs:58–64`。

**关联改动**：`5aa733b`，与 `d9f9ad2` 的版本补偿机制未衔接。

accepted 分支派发的是 `ChangeSet::empty`，dispatcher 直接忽略；failed/retryable/uncertain 及认领为 sending 的路径没有状态变更事件。相关写入也不 bump `accounts.change_version`。前端虽然有 `getSendState` Port/Adapter，但没有消费该接口的 feature 轮询。

**触发与影响**：用户发送后停留在当前会话，没有其他邮件变更。后端已经 accepted 或 failed，前端仍显示“排队发送”；焦点恢复时版本相同也无法靠版本差异发现这次变化。其他操作引发重新查询时才可能偶然刷新。

**最小修复方向**：状态变更事务同时 bump 版本，提交后派发包含 message/session ID 和版本的真实 ChangeSet；覆盖失败和不确定状态。

**怎么改及为什么**：复用已有 ChangeSet 和账号版本机制，将实际状态变化、版本更新放在同一事务，由 runtime 在成功提交后通知 UI；覆盖认领、正常结果、失败和启动恢复。条件更新未生效时不要凭旧结果发事件。原因是事件负责及时性、持久版本负责丢事件后的补偿，两者缺一都会留下盲区。无需另加高频状态轮询来掩盖后端漏通知。

**回归场景**：保持会话打开，分别让发送成功、认证失败及结果未知，确认不依赖其他同步事件也能刷新状态；模拟事件丢失后由账号版本补偿刷新。

## R10 · P2 · Sent 副本确认与普通会话展示未闭环

**位置**：`src-tauri/src/infrastructure/repository/archive_tasks.rs:154–177`；`src-tauri/src/runtime/archive_worker.rs:111–123`；`src-tauri/src/infrastructure/repository/messages.rs:364、389`；`src-tauri/src/infrastructure/repository/sessions.rs:433、457`。

**关联改动**：`de287d3` 的归档功能和 `c49390e` 的发送记录可见性调整。

`confirm_location` 仅有定义，没有同步流程调用；客户端 APPEND 成功直接写 `confirmed`，但 `confirmed_message_id` 为 None，而 `confirm_location` 的允许状态又不包含 confirmed。无位置的本地发送记录只要任务不是 cancelled，就继续进入普通会话查询。同步发现 Sent 副本时按位置创建独立消息，这是正确的身份规则，但缺少设计约定的发送状态区与普通消息区展示分离。

**触发与影响**：例如 Graph 发送后服务器自动保存 Sent，随后同步到同一会话；普通消息列表同时保留本地发送记录和真实 Sent 副本，出现重复气泡。手动配置 server_saved 后归档任务也不会因副本出现而收敛。

**最小修复方向**：按 Task 14 将无位置记录放在发送状态区；普通会话使用实际位置消息。有确定位置证据时关联 `confirmed_message_id`，不按 Message-ID/正文猜测合并不同位置。仅凭 APPEND 成功而没有位置映射时，不宣称位置关联已完成。

**怎么改及为什么**：先对齐 confirmed 的定义，区分“服务器确认写入”和“已关联本地确定位置”，允许后续位置证据完成关联；有 APPENDUID 等确定证据时由协议适配器转换为统一位置，再由用例事务关联消息和任务。同步缺少可靠关联证据时保持待核对，不仅凭相似内容确认。与此同时调整查询和展示，让无位置发送记录仍可在任务区域查看，但不与实际 Sent 邮件混在普通列表。原因是显示重复来自两类记录混显，不能通过跨位置合并或删除未确认发送记录来解决。若某协议缺乏自动关联所需证据，应明确能力限制，不能以猜测补全。

**回归场景**：发送并同步 Sent，普通会话仅出现实际 Sent 消息，发送状态区保留任务状态；验证不同账号及不同位置实体仍独立。
