# Vue 3 低侵入式国际化方案

项目：Vue 3 + TypeScript + Vite + Tauri 2。

底层使用 `vue-i18n`，**业务组件不直接依赖 `$t()` / `useI18n()`** 编写静态 UI 文案。

核心原则：**中文优先、编译期转换、零侵入开发、显式排除、运行时切换语言**。

---

## 1. 设计目标

实现一套基于 Vite 插件和 Vue AST 的自动国际化机制，使业务开发者可以直接用中文编写 UI，无需手动写 `$t()`、`useI18n()` 或维护翻译 Key。

要求：

- 中文作为默认开发语言和回退语言。
- 自动识别 Vue 模板中的中文 UI 文本。
- 编译期自动转换为 `vue-i18n` 翻译调用。
- 自动提取中文并生成多语言资源文件。
- 支持运行时切换语言，无须重新构建。
- 不修改业务组件原始代码。
- 不对用户数据、邮件正文等动态内容自动翻译。
- 支持 Windows、macOS 和 Linux 桌面环境。

### 两条硬限制（必守）

1. **禁止运行时扫描整页 DOM 做翻译替换。** 客户端会展示大量 Outlook 邮件内容；DOM 扫描极易误改邮件正文、联系人姓名等用户数据。国际化只发生在 **编译期对 Vue 模板 AST 的静态转换** + **运行时 vue-i18n 查表**。
2. **禁止在每次 `vite build` 时自动覆盖翻译文件。** 提取、人工翻译、校验、编译必须是独立阶段；否则语言资源易冲突、人工译文被冲掉。

## 2. 技术选型

| 依赖 | 用途 |
|---|---|
| `vue-i18n` | 运行时翻译、语言切换 |
| `@vue/compiler-sfc` | 解析 Vue SFC |
| `@vue/compiler-dom` | 解析 Template AST |
| `vite` | 编译期插件集成 |
| `magic-string` | 按 AST 源码位置做非破坏性转换 |
| `typescript` | 必要时解析 TS/JS 表达式 |
| JSON | 多语言资源 |

---

## 3. 自动国际化工作流程

```
Vue SFC 源码
    ↓
Vite 国际化插件
    ↓
Vue SFC / Template AST 解析
    ↓
识别用户可见中文文本
    ↓
判断是否满足自动转换规则
    ↓
提取中文原文作为翻译 Key
    ↓
生成或更新语言资源（仅 extract 命令，非每次 build）
    ↓
转换为 vue-i18n 调用
    ↓
交给 Vue 正常编译
    ↓
运行时根据当前语言显示翻译
```

注意插件顺序与 Vue SFC 编译阶段，确保 AST 分析的是**原始模板**，而不是已经编译的 JavaScript。

---

## 4. 自动转换规则

### 4.1 默认自动转换

处理：

- Vue 模板中的静态中文文本节点。
- `placeholder`、`title`、`aria-label`、`alt` 等用户可见属性。
- 明确声明为可翻译的组件属性（白名单，二期）。
- 包含纯中文或中英文混合内容的静态 UI 文案。

示例（业务源码保持中文，不变）：

```vue
<template>
  <h1>收件箱</h1>
  <button title="发送邮件">发送</button>
  <input placeholder="搜索邮件" />
</template>
```

编译时转换为等价逻辑：

```vue
<template>
  <h1>{{ $t('收件箱') }}</h1>
  <button :title="$t('发送邮件')">
    {{ $t('发送') }}
  </button>
  <input :placeholder="$t('搜索邮件')" />
</template>
```

### 4.2 默认不自动转换

- `<script>`、`<style>` 中的内容（一期；TS 静态串提取为后期）。
- Vue 动态插值中的变量。
- API 响应。
- 用户姓名、联系人姓名。
- 邮件主题、邮件正文、附件名称。
- URL、文件路径、SQL、正则表达式。
- `class`、`id`、`key` 等技术属性。
- `v-model`、`v-for` 等表达式。

**禁止**扫描渲染后的整个 DOM 并替换文字。

### 4.3 动态文案

动态文案显式国际化：

```ts
$t('共有 {count} 封邮件', { count })
```

或提供统一辅助函数。复数、日期、数字等使用 `vue-i18n` 标准能力，不通过正则推断。

### 4.4 显式排除

统一排除机制，支持排除整个子树，例如：

```vue
<div v-no-i18n>中文原始内容</div>
```

具体指令名与编译期实现在插件设计中敲定；邮件正文渲染容器必须默认排除或落在不可扫描区域。

## 5. 翻译 Key 设计

第一阶段直接使用中文原文作为 Key：

```json
{
  "收件箱": "Inbox",
  "发送邮件": "Send Email",
  "搜索邮件": "Search mail"
}
```

- 默认语言 `zh-CN`，初期支持 `en-US`。
- 缺失翻译回退到中文。
- 相同中文自动去重。
- **已有翻译不得被自动覆盖。**
- 中文原文修改后，能识别新增 Key 与潜在废弃 Key。
- 支持未来为同词不同义设置上下文 Key。
- 对含 `{}`、`.` 等特殊字符的文案设计安全的 Key 编码策略，避免与 `vue-i18n` 消息语法或路径解析冲突。

---

## 6. 语言资源生成

构建插件负责转换；**提取不得绑在普通 `vite build` 上覆盖人工翻译**。

独立命令：

```bash
pnpm i18n:extract
pnpm i18n:check
```

| 命令 | 职责 |
|---|---|
| `i18n:extract` | 扫描、去重、合并新词条；稳定排序写入语言文件；不覆盖已有译文 |
| `i18n:check` | 缺失翻译、失效 Key、不支持的动态表达式 |

生产构建默认只读取已生成的语言资源；必需翻译缺失时按可配置策略警告或失败。

阶段分离：

```
开发写中文 → i18n:extract → 人工补 en-US → i18n:check → vite build / tauri build
```

---

## 7. 运行时语言切换

由全局 `vue-i18n` 实例负责：

- 默认使用系统语言（仅在受支持语言范围内）。
- 用户可手动选择；手动设置优先于系统语言。
- 用户设置持久化（本地存储 / 账户设置，实现期定）。
- 切换后当前界面即时更新；**不**重启 Tauri 应用。
- 支持回退到 `zh-CN`。

---

## 8. 架构约束

国际化是独立基础设施，**不得与邮件业务逻辑耦合**。

建议目录：

```
src/
  i18n/
    index.ts
    locales/
      zh-CN.json
      en-US.json

plugins/
  vite-plugin-auto-i18n/
    index.ts
    parser.ts
    transform.ts
    extractor.ts
    rules.ts
```

- 邮件同步、Graph API、SQLite、Rust 业务层不感知 Vue 自动 i18n。
- Rust 返回**结构化业务状态码**；前端再映射为本地化 UI 文案。
- 前端业务 Port/Adapter 返回领域数据（原文）；展示层静态壳文案走自动 i18n，动态业务字符串按显式 `$t` 或状态码映射。

与 `AGENTS.md` 对齐：业务组件仍通过 Port 取数；i18n 属于 UI 基础设施，不是 RS 桥职责。

---

## 9. 质量要求

自动化测试须覆盖：

- 普通中文文本 / HTML 属性 / 组件属性转换
- 中英文混合文本
- 插值表达式
- 转义字符及特殊符号
- `v-if`、`v-for` 等结构
- 排除指令
- 相同文案去重
- 热更新 HMR
- 多语言实时切换
- 生产构建
- 保留原始源码及 Source Map
- 不破坏 Vue 指令和组件编译行为
- **不修改邮件正文和其他动态数据**

---

## 10. 实施原则

1. 先做可验证 MVP：仅模板静态文本节点 + 标准可见属性。
2. 稳定后再加：组件属性白名单、复杂动态文案、TS 静态字符串提取。
3. 优先复用 Vue 编译器 AST 与转换机制；**不**自行用正则整文件替换模板。
4. 绝不采用「挂载后遍历 DOM 替换文本」方案。

**最终目标：业务开发者正常编写中文 Vue 组件，由编译基础设施自动完成国际化，不增加常规 UI 开发的编码负担。**
